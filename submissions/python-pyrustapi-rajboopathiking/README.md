# Python + PyRustAPI

| | |
|---|---|
| Language | Python 3.12 (CPython) |
| Framework | PyRustAPI 2.0.1 (Tokio / Hyper Core) |
| Server | Native Rust Tokio/Hyper runtime (single worker, matching the 1 vCPU target) |
| SQLite driver | standard library `sqlite3` module (in-process autocommit WAL) |
| JSON | SQLite `json_object` / `json_group_array` + `orjson` 3.12.0 |
| **Nginx or direct** | **Direct**: serves `0.0.0.0:80` directly |

---

## Running It

```bash
sudo bash install.sh   # Installs Python 3.12, venv, and build tooling
bash build.sh          # Creates .venv and installs requirements.txt
SQLITE_PATH=... JWT_SECRET=... HOST=0.0.0.0 PORT=80 bash start.sh
```

## Optimizations & Architectural Rationale

1. **Direct Mode (Bypassing Nginx)**:
   - On a single-vCPU droplet, running Nginx consumes **15–20% of CPU capacity** that is better allocated directly to SQLite query processing.
   - PyRustAPI is backed by a native Rust **Tokio / Hyper engine**. Measured with 10,000 concurrent keep-alive k6 users: 795.7 req/s, 0.00% errors, ~100 MB memory footprint and 17.2% peak CPU. Memory scales with live sockets; the process fd budget is raised to 65,000 in `start.sh` for the 50k target.

2. **In-Database JSON Generation**:
   - The `/feed` and `/posts/{id}` endpoints utilize SQLite's native `json_group_array()` and `json_object()` functions. JSON documents are constructed directly inside SQLite's optimized C core, completely bypassing intermediate Python dictionary creation and memory allocations.

3. **Zero-Allocation Error Responses**:
   - All error responses (`404 not found`, `400 invalid id`, `401 missing token`, etc.) are pre-allocated as static byte `Response` objects at startup, incurring 0 runtime allocation overhead during validation failure paths.

4. **In-Line Autocommit SQLite Execution**:
   - Every query is an indexed primary-key or covered index lookup that executes in sub-millisecond time.
   - Using `sqlite3` with `isolation_level=None` (autocommit) commits each write statement immediately before the response is sent, fulfilling Rule 6 durability.
   - Running inline avoids process context switches and inter-thread hops on a single-core machine.

5. **Pragmas**:
   - `PRAGMA journal_mode = WAL`
   - `PRAGMA synchronous = NORMAL` (Rule 6 compliant)
   - `PRAGMA mmap_size = 1073741824` (1 GiB memory-mapped I/O through OS page cache)
   - `PRAGMA cache_size = -65536` (64 MiB page cache)
   - `PRAGMA temp_store = MEMORY`

6. **Handcrafted Constant-Time JWT Verification**:
   - Custom HS256 HMAC-SHA256 signature verification and payload validation executed per request without caching (Rule 5 compliant).

7. **Garbage Collection Tuning**:
   - Startup objects are frozen via `gc.freeze()`, and generation thresholds are raised to avoid unnecessary GC cycles during sustained request traffic.

## 📊 Empirical Performance Results (k6 Load Test)

### Sustained challenge workload

6,000 VUs, 60s ramp-up, 5-minute hold, each framework run in isolation on the same
machine and seed database (macOS, 8 logical cores):

| Metric | FastAPI (Uvicorn + uvloop) | PyRustAPI (Native Tokio/Hyper) | Performance Delta |
| :--- | :---: | :---: | :---: |
| **Throughput** | 560.6 req/s | **561.1 req/s** | **+0.1% (closed-loop)** |
| **Average Latency** | 1.04 ms | **0.79 ms** | **⚡ 24% faster** |
| **p95 Latency** | 1.92 ms | **1.53 ms** | **⚡ 20% lower latency** |
| **p99 Latency** | 3.15 ms | **2.72 ms** | **⚡ 14% lower latency** |
| **Error Rate** | 0.00% | **0.00%** | **42/42 Spec Tests Passed** |

### CPU saturation (open-loop, 3,000 req/s constant arrival)

The closed-loop test is think-time-bound; both servers keep up. Pushing a fixed
3,000 req/s exposes the per-request CPU cost:

| Metric | FastAPI (Uvicorn + uvloop) | PyRustAPI (Native Tokio/Hyper) | Performance Delta |
| :--- | :---: | :---: | :---: |
| **Achieved Throughput** | 2,975 req/s | **3,000 req/s** | **100.8% of target** |
| **Average Latency** | 46.01 ms | **0.56 ms** | **⚡ 82x lower** |
| **p95 Latency** | 129.05 ms | **0.85 ms** | **⚡ 152x lower** |
| **p99 Latency** | 217.70 ms | **2.81 ms** | **⚡ 77x lower** |
| **Error Rate** | 0.03% | **0.00%** | **Zero errors** |

At a 6,000 req/s target, PyRustAPI sustained **5,500 req/s with 0% errors**;
FastAPI collapsed to **2,222 req/s with 3.3% errors**.

### 10,000 concurrent users (2-minute hold)

The official challenge workload (`bench/load.js`), 90-second ramp-up, 2-minute hold,
against the stable PyRustAPI 2.0.1 wheel on a fresh seed database:

| Metric | Result |
| :--- | :---: |
| **Concurrent users** | **10,000** |
| **Throughput** | **795.7 req/s** |
| **Average / p95 / p99** | **0.65 ms / 1.42 ms / 3.48 ms** |
| **Error rate** | **0.00%** |
| **Peak CPU / memory** | **17.2% / ~100 MB** |

A separate 4,000 feed req/s constant-rate run completed with 100% success at 0.89 ms
average latency and ~58% of one CPU core, indicating headroom for the ~4,000-5,000
req/s generated by 50k think-time users. macOS exposes
only 16,384 ephemeral ports, so 20k+ local users cannot be generated from this laptop;
the official benchmark runs k6 on a separate machine and is the authoritative 50k test.

> Note: the published FastAPI result is **48,000 concurrent users**, not 50,000 req/s.
> The challenge scores concurrent users; 50,000 req/s would require roughly 500k users
> at the official 3-15 second think time.
