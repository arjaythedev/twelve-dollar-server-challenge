# Objective-C / raw io_uring / SQLite

Direct HTTP/1.1 on `$HOST:$PORT` (no Nginx), written in plain Objective-C on the GNUstep runtime, with no Foundation, no framework, no event library.

## Versions

- Objective-C, clang 23.1.4 (official LLVM release tarball, pinned by sha256; `install.sh` unpacks only clang, lld, llvm-profdata and clang's runtime), `-fobjc-runtime=gnustep-2.2`, manual memory management
- libobjc2 2.3 (GNUstep runtime), robin-map 1.4.0, liburing 2.15, SQLite 3.54.1 amalgamation: all pinned by sha256 and built from source by `build.sh` (SQLite is stock, unpatched)
- Needs Linux 6.1+ (DEFER_TASKRUN); the grader's 6.8 kernel is fine. Ubuntu's 6.8.0-147 refuses a buffer-ring registration whose reserved words are all zero (an inverted check, Launchpad #2162843), so a refused registration is retried once with `resv[0]=1`

## Design

- Own root class `TDObject` (no NSObject). Connections are `TDConn` instances placed in a slab indexed by their io_uring fixed-file slot; hot methods are `objc_direct`; route handlers are objects whose IMPs are looked up once and called directly.
- One thread drives 8 io_urings: multishot direct accept, multishot recv into a provided buffer ring per ring, sends on fixed descriptors. Accepted sockets live in io_uring fixed-file tables, not the process fd table, so 8 rings × 65,535 slots lift the connection ceiling past `LimitNOFILE=65535`. Accept fills ring 0 first and moves to the next ring at a high-water mark 4,096 slots below full (a full table makes the kernel drop the socket it just accepted), so below ~61k connections only one ring is in use and none is dropped at a switch; ring 0 waits and holds a multishot poll on each other active ring's fd. One thread instead of a thread per ring: on one vCPU the threads only added context switches and lock convoys (p99 33 ms vs 4 ms in our A/B).
- Under load (8+ requests in the last pass) the loop waits for up to 128 completions or 1 ms before processing, so batches and group commits get bigger and `io_uring_enter` calls fewer (idea from #32).
- Every ring is `SINGLE_ISSUER | COOP_TASKRUN`, and ring 0 (the one the thread waits on) also `DEFER_TASKRUN`: completions are processed in batches.
- One SQLite connection (WAL, `synchronous=NORMAL`, no mmap, a 256 MB page cache limit (it holds ~50 MB after startup and ~110 MB after a 5-minute hold), persistent prepared statements). Each loop iteration runs its whole completion batch (all rings) in one transaction (group commit) and submits every response only after `COMMIT` succeeds; if a commit fails, the batch's connections are dropped, so no 201 is ever sent for an uncommitted row.
- Checkpoints run in a child process, forked at startup before any SQLite or io_uring state exists. The loop asks it (over a pipe, answer read through io_uring) for a `PASSIVE` checkpoint every 2,000 new WAL frames, so the copy and its two fsyncs never block the loop. Under constant writes a passive pass can never copy the whole WAL, so the WAL could not rewind and would grow without bound. When it reaches 8192 frames (~32 MB), writes wait until one pass copies everything; the next write then rewinds the WAL. Reads are answered during that wait. A write, and every later request on the same connection, stays at the front of the batch until the wait ends, so pipelined responses keep their order. The wait is ~40–80 ms every ~1.5 s with an 11 ms-fsync disk, with a 250 ms cap. If the child dies, SQLite's own autocheckpoint takes over inline (every 250 frames). The second process needs the shared-memory WAL index, so locking is `NORMAL`, not `EXCLUSIVE`: the extra file locks measured as noise (11.56 vs 11.54–11.60 µs/req).
- At the memory wall the kernel evicts file pages first, and a loop that then reads the database from disk stops answering while requests pile up in sockets at 3-4 KB each. Pages in SQLite's own cache are anonymous memory, so they stay. At startup the server reads the `likes` unique index, `posts_user_id_idx` and `users` into that cache (`--warm`), since inserts touch them at random. The checkpointer drops the file pages it has synced (`posix_fadvise`, `--ckdrop`). `journal_size_limit=0` truncates the WAL at the first commit after a rewind, so later frames append instead of overwriting old file pages. That first commit carries a single write (`--onewrite`), because its frames still overwrite old pages, and each page already evicted is read from disk before a partial write. The code and libraries are `mlock`ed within `RLIMIT_MEMLOCK` (`--lock`).
- Read first, answer later. Each pass reads every completion but answers at most 512 requests; the rest stay parked in a queue. A parked request costs a 64-byte record, while one left in its socket costs a kernel buffer. After a burst empties the buffer ring (1 KB × 1,024 per ring), a pass re-arms only as many receives as there are free buffers, oldest first (`--rearm`), since re-arming them all only ends them again with `ENOBUFS`.
- Newest first in a backlog (`--lifo`). A reply sent more than 40 ms after its request costs the kernel an extra bare ACK, about a fifth more CPU per request on our test box. Oldest-first service makes every newcomer that late too once a backlog exists, and the extra CPU can keep that backlog alive at a load the server otherwise handles. So when more than one pass of requests is parked, the newest go first and the oldest get a share of each pass that grows with their age: an eighth up to 62 ms, all of it at 250 ms (`--lifoage`). A connection's own requests stay in order. Nothing is dropped, and the rule applies to any backlog.
- SQLite's page cache comes through its public `SQLITE_CONFIG_PCACHE2` plugin API (`td_pcache` in `src/td_btree.c`, `--pcache`): an array indexed by page number, a clock instead of an LRU list. The stock cache scans its whole hash table at the next commit after each B-tree split, about 30 times a second under load at ~350 µs each, because the split parks a page under the pending-byte page number.
- Every request reads SQLite while it is served, and every JWT signature (HS256, own SHA-256) and `exp` is verified on each request.
- `/feed` and `GET /posts/:id` read SQLite's B-tree layer through its own cursor calls, with no bytecode engine (`src/td_btree.c` includes the stock amalgamation, so `sqlite3BtreeCursor`, `First`, `Next`, `Previous`, `TableMoveto`, `IndexMoveto` and `PayloadFetch` are reachable). Pages still come through SQLite's pager, page cache, WAL and locks, inside the batch's transaction. `/feed` walks `posts_created_at_id_idx` from its first entry (the index is DESC, so newest first) for 20 ids, counts their likes with one `likes_post_id_idx` range scan when the ids span fewer than 256 (one seek per post otherwise), then seeks each post by rowid (the newest from the table's last row, then one step back when ids are consecutive) and its author in `users`. The four read cursors are opened on first use within a batch and closed before its `COMMIT`; when a write in the same batch changes a tree, SQLite saves and reseeks them as it does for any open statement cursor. Nothing else is kept between requests except root page numbers, checked against the schema cookie on every call. A row the fast path does not cover (a record on overflow pages, an unexpected column type) sends the request to the SQL statements, which are still prepared (`--btree=0` uses them for every read).
- clang PGO: `pgo/train.m` builds a synthetic database (no seed data) and drives the store, JSON and JWT code; everything is then rebuilt with the profile. Falls back to a plain `-O3` build if any PGO step fails.

## HTTP handling

Own parser: request line, `Content-Length`, `Authorization` and `Connection` are read; query strings are ignored. Keep-alive by default on HTTP/1.1, `Connection: close` and HTTP/1.0 (without `keep-alive`) close after the response. Pipelined requests are answered in order. A request larger than 16 KB, or one with `Transfer-Encoding`, is dropped without a response (no 201 can be sent for it). `Expect: 100-continue` gets no interim response; clients send the body after their timeout and get the normal answer.

Did not help (reverted): a JSON escaper that stores each clean 8-byte block as it tests it (+1.9 % `/feed` instructions); WAL hold at 4,096 or 16,384 frames instead of 8,192, a 16 MB page cache, a 2 ms / 256-completion batching window (noise or worse at 300,000 users on the Synteq box); bigger `wal_autocheckpoint` (4096: −4% CPU on tmpfs, double the p99 on disk); response header written into the body's headroom (+0.5%, noise); AVX2 scan in the JSON escaper (−2%: bodies are short); streaming feed rows without the row copy (noise); a 256 MB page cache at 100,000 users, off the memory wall (more CPU than 32 MB; at 300,000 users it's what keeps the server alive, see above); extra SQLite `OMIT_*`/`UNTESTABLE` compile options (noise); PGO that also profiles the running server over loopback (noise).

Removed after review: a one-line patch to the SQLite amalgamation (`balance_nonroot` parked a page under `nPage+1` instead of the pending-byte page number; create-only wrk +8%, realistic mix −0.5% CPU). Arjay ruled on 2026-10-31 that the engine has to be stock SQLite (rule 2), so build.sh no longer edits it.

Memory: at 100,000 idle connections the cgroup holds 407 MB, of which 20 MB is the process (anon) and the rest kernel socket and io_uring memory (~3.9 KB per connection), so 2 GB holds more connections than the 8 × 65,535 slots.
